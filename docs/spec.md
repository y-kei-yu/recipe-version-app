# レシピのバージョン管理アプリ v4

## 背景

料理は分量や手順を少し変えるだけで、結果が大きく変わる。
自分好みの味を探して試行錯誤しているが、紙のメモでは変更のたびに書き直しになり、
「どの回に、どの分量・手順で作ったか」を追えなくなる。

## 概要

料理レシピを上書きせず、バージョンとして積み重ねて管理するアプリ。

- レシピを変更するたびに新しいバージョンとして保存する
- バージョン間の差分（分量・手順の変更）を確認できる
- バージョンごとに「作ってみた結果（評価・感想）」を記録できる

「どの条件で作ったときが一番良かったか」をいつでも確認できる状態を目指す。

## 実装方針

- Server Components を基本とし、データ取得はサーバー側で行う
- フォーム入力やボタン操作が必要な部分のみ Client Component にする
- データの作成・更新・削除は Server Actions で行う
- バリデーションは Zod スキーマを1か所に定義し、クライアント・サーバーの両方で使う（サーバー側の検証を正とする）
- 初回作成時は `Recipe` と `RecipeVersion v1` を同時に作成する
- 編集時は既存データを上書きせず、新しい `RecipeVersion` を作成する
- 差分計算は UI から切り離した純粋関数として実装し、単体テストの対象にする
- MVP2〜3は仮データで画面を作成し、MVP4完了時点でDB連携に切り替える

## 画面構成

- `/recipes`
  - レシピ一覧画面

- `/recipes/new`
  - レシピ作成画面

- `/recipes/[id]`
  - レシピ詳細画面（デフォルトで最新バージョンを表示）

- `/recipes/[id]/versions/new`
  - 新しいバージョン追加画面（レシピ編集画面を兼ねる）
  - 最新バージョンの材料・手順を入力済みの状態で開く
  - `?base=[versionNumber]` を付けた場合は、指定バージョンの内容を入力済みにする（過去バージョンからの復元）

- `/recipes/[id]/versions/[versionNumber]`
  - 特定バージョンの詳細表示画面

- `/recipes/[id]/diff?from=[versionNumber]&to=[versionNumber]`
  - 差分確認画面（クエリパラメータで比較する2つのバージョンを指定する）

すべての画面はスマートフォン幅（375px）で崩れないことを前提とする（台所で見るため）。

| カラム名 | 型 | 必須 | 説明 |

| ingredients | String | ○ | 材料（改行区切りで保存・最大2000文字） |
| steps | String | ○ | 手順（改行区切りで保存・最大5000文字） |
| changeMemo | String | - | 何を変えたかのメモ（最大500文字） |
| rating | Int | - | 作ってみた評価（1〜5） |
| resultMemo | String | - | 作ってみた感想（最大500文字） |
| createdAt | DateTime | ○ | 作成日時 |

**ユニーク制約：`recipeId` と `versionNumber` の組み合わせは一意**

---

### ingredients / steps の保存フォーマット

`ingredients` と `steps` は改行区切り（`\n`）の文字列として保存する。

```
# ingredientsの例
玉ねぎ 1個
にんじん 1本
カレールー 1箱

# stepsの例
玉ねぎとにんじんを切る
鍋に油を熱し、野菜を炒める
水を加えて煮込む
```

保存時に以下の正規化を行う（差分に無意味な変更が出ないようにするため）。

- 改行コードを `\n` に統一する
- 各行の前後の空白を取り除く
- 空行を取り除く

文字数の上限はDBの型（`Text`）ではなく、Zod によるバリデーションで制限する。

## リレーション

Recipe と RecipeVersion は、1対多の関係にする。

- 1つの Recipe は、複数の RecipeVersion を持つ
- 1つの RecipeVersion は、1つの Recipe に紐づく
- Recipe を削除した場合、関連するすべての RecipeVersion も削除する（`onDelete: Cascade`）

```prisma
model Recipe {
  id                  Int             @id @default(autoincrement())
  title               String          @db.VarChar(100)
  description         String?         @db.VarChar(500)
  latestVersionNumber Int             @default(1)
  createdAt           DateTime        @default(now())
  updatedAt           DateTime        @updatedAt
  versions            RecipeVersion[]

  @@map("recipes")
}

model RecipeVersion {
  id            Int      @id @default(autoincrement())
  recipeId      Int
  versionNumber Int
  ingredients   String   @db.Text
  steps         String   @db.Text
  changeMemo    String?  @db.VarChar(500)
  rating        Int?
  resultMemo    String?  @db.VarChar(500)
  createdAt     DateTime @default(now())
  recipe        Recipe   @relation(fields: [recipeId], references: [id], onDelete: Cascade)

  @@unique([recipeId, versionNumber])
  @@map("recipe_versions")
}
```

例：

- カレー
  - v1 初回作成
  - v2 はちみつを追加（評価4：コクが出た）
  - v3 水の量を調整（評価5：これが一番）

# バージョン管理のルール

## 用語

### Recipe

レシピの親データ。

管理する内容：

- レシピ名
- 説明
- 最新のバージョン番号
- 作成日時
- 更新日時

---

### RecipeVersion

レシピの各バージョンのデータ。

管理する内容：

- 材料
- 手順
- 変更内容のメモ
- 作ってみた評価・感想
- バージョン番号
- 作成日時

---

## バージョン番号のルール

- 初回作成時は `versionNumber = 1` とする
- レシピを編集した場合、新しいバージョンを作成する
- 既存バージョンの材料・手順・変更メモは更新しない（上書きしない）
- `versionNumber` は 1 ずつ増加する
- 同一レシピ内で同じ `versionNumber` は存在しない

例：

- カレー
  - v1 初回作成
  - v2 はちみつを追加
  - v3 水の量を調整
  - v4 塩を少し減らす

### 更新してよい項目（例外）

`rating` と `resultMemo` のみ、バージョン作成後に更新できる。

理由：

- 評価と感想は、実際に作った後でないと書けないため
- 材料・手順（＝実験の条件）は変えず、結果だけを後から書き足す形にするため

---

## 初回作成時の処理

レシピ作成時は、Recipe と RecipeVersion v1 を同時に作成する。
`changeMemo` は初回作成のため入力欄を出さない。

処理の流れ：

1. ユーザーがレシピを作成する
2. Prismaの `$transaction` を使い、以下を同時に実行する
   1. `Recipe` を `latestVersionNumber = 1` で作成する
   2. `RecipeVersion` を `versionNumber = 1` で作成する

---

## 編集時の処理

レシピを編集した場合は、既存データを更新せず、新しいバージョンを作成する。
`changeMemo` は任意入力とし、何を変えたかをユーザーが記録できる。

入力画面は、最新バージョン（または `base` で指定したバージョン）の材料・手順が入力済みの状態で開く。

処理の流れ：

1. Prismaの `$transaction` を使い、以下を順に実行する
   1. `Recipe.latestVersionNumber` を 1 増やす（`increment`）
   2. 増やした後の値を `versionNumber` として、新しい `RecipeVersion` を作成する

```ts
await prisma.$transaction(async (tx) => {
  const recipe = await tx.recipe.update({
    where: { id: recipeId },
    data: { latestVersionNumber: { increment: 1 } },
  });

  return tx.recipeVersion.create({
    data: {
      recipeId,
      versionNumber: recipe.latestVersionNumber,
      ingredients,
      steps,
      changeMemo,
    },
  });
});
```

### 同時アクセス時の採番について

- 「最大の `versionNumber` を読んで +1 する」方式は、トランザクション内であっても、
  PostgreSQL の既定の分離レベル（Read Committed）では2つの処理が同じ値を読めてしまい、重複が起きる
- そのため、親の `Recipe` 行を `UPDATE` して行ロックを取り、その結果の値で採番する
  - 後から来た処理は、先の処理がコミットするまで待たされるため、同じ番号にならない
- `recipeId + versionNumber` のユニーク制約は、万が一の最終防衛線として残す
- 副次的な効果として、バージョン追加時に `Recipe.updatedAt` も更新される
- 対象の `Recipe` が存在しない場合（`P2025`）は 404 とする

---

## 最新バージョンの定義

最新バージョンは、`versionNumber` が `Recipe.latestVersionNumber` と一致する RecipeVersion とする。

---

## 表示時のルール

### 一覧画面

- レシピ名、説明、最新バージョン番号、更新日を表示する
- 更新日の新しい順に並べる

### 詳細画面

- デフォルトでは最新バージョンを表示する
- 評価・感想が入力済みの場合は表示する

### バージョン履歴

- すべてのバージョンを `versionNumber` の降順で表示する
- 各バージョンに、作成日時・変更メモ・評価を表示する

表示例：

- v4 塩を少し減らす
- v3 水の量を調整 ★5
- v2 はちみつを追加 ★4
- v1

---

## 削除時のルール

### レシピを削除した場合

Recipe を削除した場合、関連するすべての RecipeVersion も削除する。
Prismaスキーマで `onDelete: Cascade` を設定することで実現する。

### バージョン単体の削除

MVP段階では、バージョン単体の削除は行わない。

理由：

- 履歴を残すことを優先するため
- 誤って過去の履歴を削除しないようにするため

---

## 差分比較のルール

任意の2つのバージョンを比較できるようにする。

比較対象：

- 材料（ingredients）
- 手順（steps）

比較方法：

- `ingredients` と `steps` を改行で分割し、行単位で差分を検出する
- 変更された行（削除と追加が隣り合う行）は、行内を文字単位で比較し、変わった部分だけを強調する
  - 例：`砂糖 大さじ1` → `砂糖 大さじ2` の場合、`1` と `2` だけを強調する
- 差分計算は `diff`（jsdiff）を使い、`diffRecipeText(oldText, newText)` のような純粋関数として実装する
- 表示は自前のコンポーネントで行う（追加＝緑、削除＝赤）

`react-diff-viewer` を使わない理由：

- 本家の更新が止まっており、現行の React で動く保証がないため
- コード用の表示（行番号、等幅フォントなど）が中心で、レシピの表示に合わないため
- 差分の判定ロジックを自分のコードとして持ち、テストできるようにするため

既知の制約：

- 手順の順番を入れ替えた場合、「移動」ではなく「削除＋追加」として表示される

URLの形式：

```
/recipes/[id]/diff?from=1&to=3
```

例：

- v2 と v4 を比較する → `/recipes/1/diff?from=2&to=4`
- `from` が `to` より大きい場合は、小さい方を旧バージョンとして扱う

---

## エラー時のルール

考え方：URLのパス部分が指すものが存在しない場合は 404、クエリパラメータの誤りは画面内のエラーメッセージとする。

| ケース | 対応 |
|---|---|
| レシピIDが存在しない／数値でない | 404ページを表示する |
| `/versions/[versionNumber]` のバージョン番号が存在しない／数値でない | 404ページを表示する |
| 差分画面で `from` または `to` が欠けている | エラーメッセージを表示する |
| 差分画面で `from` または `to` が数値でない | エラーメッセージを表示する |
| 差分画面で `from` または `to` が存在しないバージョン番号 | エラーメッセージを表示する |
| 差分画面で `from` と `to` が同じ | エラーメッセージを表示する |
| `/versions/new?base=` が存在しないバージョン番号／数値でない | `base` を無視し、最新バージョンを入力済みにする |

差分画面のエラーメッセージには、レシピ詳細画面へ戻るリンクを付ける。

---

## 制約

同一レシピ内で同じ `versionNumber` を作成しない。

そのため、以下の制約を設ける：

- `recipeId` と `versionNumber` の組み合わせは一意（重複不可）
- Prismaスキーマで `@@unique([recipeId, versionNumber])` を設定する

---

## 公開範囲とアクセス制限

MVP段階ではログイン機能を持たない（利用者は自分1人を想定）。

ただし、公開URLを知っている人が誰でも登録・削除できる状態を避けるため、
本番環境は Basic 認証で保護する。

- Next.js の Middleware（Next.js 16 では `proxy.ts`）で実装する
- ユーザー名とパスワードは環境変数で管理する
- 選考用に、READMEにデモ動画またはスクリーンショットを載せる

ログイン機能（ユーザーごとのレシピ管理）はMVP後に追加する。
その際に `users` テーブルと `recipes.userId` を追加する。

## テスト方針

「表示されるか」よりも「ロジックが正しいか」を重点的にテストする。

| 種類 | 対象 | ツール |
|---|---|---|
| 単体テスト | 差分計算、入力の正規化、Zodスキーマ | Vitest |
| 結合テスト | Server Actions とDB（採番、同時実行、カスケード削除） | Vitest + PostgreSQL（Docker／CIではサービスコンテナ） |
| コンポーネントテスト | フォームのエラー表示、0件表示など、分岐のある部分のみ | React Testing Library |
| E2Eテスト | 作成 → バージョン追加 → 差分表示 の1本 | Playwright |

## 設計判断の記録（ADR）

判断の理由を `docs/adr/` に1件あたり数行で残す。

- 0001 編集を上書きではなく新バージョン作成にした理由
- 0002 材料・手順を構造化せず、改行区切りの文字列にした理由
- 0003 採番を `latestVersionNumber` の更新で行う理由
- 0004 差分表示をライブラリではなく自前で実装した理由
- 0005 評価・感想だけを更新可能にした理由
